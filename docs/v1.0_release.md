# Content Factory v1.0

## Release definition

v1.0 is the first usable personal Content Factory web application. It is not an enterprise multi-tenant SaaS and does not claim that every media provider is production-integrated.

The release closes the core user workflow:

`brief → research → evidence → knowledge review → editorial → content spec → script → asset jobs → assembly → QC → human approval → export → publication → observation → learning`

The server enforces lifecycle transitions; the browser is only a client.

## v1.0 acceptance criteria

- A user can create a durable ContentRun through the web UI.
- A factory run can research a brief, persist candidate knowledge, pause for human promotion, then resume.
- Accepted knowledge is the only durable knowledge basis used for editorial generation.
- Editorial ideas, ContentSpec, script, production requests, assets and QC retain claim/evidence provenance.
- Stub/local providers make the complete workflow testable without paid credentials.
- Production jobs have durable state and can be inspected.
- Assembly creates a deterministic output package.
- QC must pass before approval.
- Approval requires an explicit decision reference.
- Export requires approval and produces a hashable manifest.
- Publication requires an exported run; publication and observation remain separate durable events.
- Learning is a candidate until explicitly promoted.
- Replay identifies affected assets from claim provenance rather than regenerating the entire run.
- Protected product API endpoints require the factory API token and apply request/rate limits.
- Unexpected server errors return a generic response while details remain in server logs.
- CI verifies the Python test suite and container build.
- The application binds to the configured PORT and exposes /health.

## Rendering modes

`FACTORY_RENDERER=package` exports the assembled content package. It does not pretend that JSON is a video.

`FACTORY_RENDERER=whisper_studio` enables actual video rendering through the local Whisper Studio integration. The integration requires a configured Whisper Studio checkout and is covered by an opt-in external test.

## Deployment

The repository contains a Docker/Render deployment definition with:

- port 8080;
- /health health check;
- /data application state;
- a persistent Render disk;
- environment-based secrets.

The existing lightweight Python Render service is a development/preview deployment unless its filesystem is backed by persistent storage. A production v1.0 deployment should use the repository's persistent-disk deployment definition.

## Security baseline

The release follows a bounded subset of OWASP ASVS concerns relevant to a single-user application: authentication of protected APIs, server-side input limits, workflow-state enforcement, rate limiting, generic unexpected-error responses, and separation of authorization from browser UI.

This is not a claim of ASVS certification or a penetration test.

## Explicit non-goals

- multi-tenant accounts and billing;
- background distributed job infrastructure;
- Kubernetes, Kafka, Redis or a custom agent framework;
- automatic promotion of research into durable knowledge;
- automatic external publishing without an explicit lifecycle step;
- pretending that a local fixture is live research;
- claiming a real video render when only a package export exists.

## Release evidence

The release is valid only when the branch CI is green and the production deployment has been verified separately. External provider tests remain explicitly marked and must not be silently represented as local success.
