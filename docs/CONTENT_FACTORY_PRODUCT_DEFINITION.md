# Content Factory — продуктовое определение

**Статус:** ADOPTED / PRODUCT SCOPE (решение владельца от 2026-10-08)  
**Режим:** собственное использование → проверка на реальной эксплуатации → *возможное* коммерческое приложение.  
**Назначение документа:** определяет, *что и для кого* мы заканчиваем; не утверждает, что все описанные функции уже реализованы.

## 1. Суть продукта

**Content Factory — самостоятельное веб-приложение для организации и автоматизации производства контента для социальных сетей: от идеи/контент-плана до проверенного материала, редакционного решения, экспорта/публикации и сохранённого опыта.**

Основное обещание: **«Дай тему или задачу → получи готовую к проверке публикацию с текстом и визуалом; доработай, утверди и выпусти её, не теряя контекст проекта».**

Продукт отвечает прежде всего за **производственный цикл**. Он не обязан сам быть автором стратегии, владельцем аккаунтов или симуляцией жизни персонажа. Успех измеряется получением пригодного контента и повторяемостью процесса, а не числом агентов, абстракций, коммитов или файлов.

### Разграничение понятий

| Уровень | Что означает | Пример |
| --- | --- | --- |
| Приложение | Content Factory — общая производственная система | Одно рабочее веб-приложение |
| Проект/контекст | Настройки и история конкретного направления контента | «Лука»; «Исторические серии» |
| Персонаж | Сущность внутри проекта, если формат её требует | Лука — виртуальный блогер |
| Контент-план/серия | Упорядоченный набор задуманных публикаций | Неделя Луки; серия об играх |
| ContentRun | Конкретное производственное исполнение/ревизии | Один пост, подготовленный на проверку |
| Артефакт | Реальный текст, фотография/изображение, пакет | PNG + подпись |
| Решение | QC и человеческое утверждение конкретной версии | ACCEPT / EDIT / REGENERATE / REJECT |
| Эффект | Экспорт или подтверждённая внешняя доставка | Экспорт Instagram; Telegram message ID |

«Проект» пока представляет собой **продуктовую потребность**: использовать существующие контракты и данные; не вводить обязательный новый класс или универсальный project-management framework без доказанного разрыва.

## 2. Пользователь, его задача, ограничения

**Первый пользователь:** владелец фабрики, который сам ведёт несколько контентных направлений и хочет минимизировать ручные операции. Возможное участие редактора/QC допускается существующими правилами решений, но создание команды, регистрации пользователей и ролей SaaS сейчас не требуется.

**Основная работа пользователя:**
1. Задать проект и контекст, формат, тему/сцену или задачу.
2. Получить план публикаций либо разовый материал.
3. Получить текст + подходящий визуальный материал (генерация, подбор или импорт — с честным статусом).
4. Увидеть источники и QC; при необходимости изменить материал или перегенерировать только нужное.
5. Явно утвердить точную версию.
6. Экспортировать или опубликовать на поддерживаемой площадке; увидеть реальное состояние доставки.
7. Позднее продолжить работу с сохранёнными материалами, правилами, решениями и историей.

**Ограничения первой версии:** без обязательных платных API, новой видеогенерации, новой многоагентной платформы, CRM, биллинга, многоарендной инфраструктуры и разработок «на вырост». Подключение провайдера — отдельная проверяемая способность; отсутствие бесплатной референсной генерации не блокирует работу с импортированным изображением.

## 3. Два приёмочных сценария одного продукта

### A. Лука — социальные сети ИИ-персонажа (первый основной пилот)

Вход: согласованный профиль/визуальные референсы, ситуация, площадка, редакционный стиль.  
Выход: **один готовый пост с настоящим изображением и подписью**, проверка сохранения личности, редакционное утверждение, экспорт Instagram, восстановление данных после перезапуска.

Существующие исходники: `docs/character/character.json`, `docs/character/luka_appearance.md`, `docs/character/references/*`, `docs/character/luka_identity_comparison_2026_10_08.md`. Семь ранних оригиналов и новый портрет хранятся в ChatGPT Library; в GitHub только манифесты и уменьшенный портрет. Их **нельзя** автоматически считать доступными внутри Codex/Render. Статус `approved_references` пока пустой.

Фабрика не должна выдавать неподтверждённую внешность за эталон; характер/биография Луки ещё не утверждены. Полноразмерный референс нужен для реальной генерации или проверки сходства. Лука — тестовый проект, **не имя нового приложения**.

### B. Тематическая серия — проверка универсальности (регрессионный пилот)

Вход: тема, исследовательский/производственный brief, контекст серии.  
Выход: русскоязычный материал с проверяемыми фактами и релевантным визуалом, QC, утверждение, экспорт/доставка.  
Опора: существующие серии про будущее, кинематограф, компьютерные игры и греческий пантеон. Не переписывать исторические данные и не перезапускать публикации; использовать безопасный тестовый материал.

**Критерий универсальности:** сценарий Луки не должен изменять стиль, знания, референсы, опыт или историю тематического проекта, и наоборот. Если общие данные пересекаются — исследовать наблюдаемое смешение и исправить минимально.

## 4. Входы, выходы и границы ответственности

**Входы:** brief/тема/сцена, форматы, язык, платформа, источники (когда нужны), утверждённая identity/стиль, проектная история, возможное импортированное изображение.

**Общий цикл:** intake → research/knowledge, когда нужно → editorial/plan → text+image production → assembly → QC → human review/edit/regenerate → approval → export/publish → observation → experience retrieval.

**Выходы:** версия публикации (текст + изображение и лицензии/происхождение), проверяемая история изменений, подтверждение экспорта/доставки, данные для следующего выпуска.

Разделять:
- исследовательские факты, творческое решение и редакторский опыт;
- созданное изображение и найденное изображение; заглушку и реальный медиафайл;
- успешный локальный тест, локальную запись `PUBLISHED` и внешнюю доставку;
- опубликованное и доказанную реакцию аудитории;
- «функция есть в коде» и «функция подтверждена реальным запуском»;
- подготовку Instagram-пакета и действующую Instagram API-интеграцию.

**Подключения сейчас:** Telegram adapter присутствует в коде; факт работоспособности конкретного E2E должен подтверждаться свежим запуском. Instagram в интерфейсе может выступать форматом результата, но реальный аккаунт/Meta API **не подтверждены**; поэтому экспорт — честный первый результат. Render preview и постоянное хранилище проверить отдельно.

## 5. Стадии продукта

### Этап I — собственное использование (ACTIVE / NOW)

Один владелец, существующее веб-приложение. Можно иметь несколько независимых контентных контекстов, не строя SaaS. Минимальные доказательства:
1. Конкретная публикация Луки: настоящий визуал + подпись + QC + human approval + экспорт, полный след provenance, восстановление после перезапуска.
2. Тематическая публикация: существующий конвейер сохранил фактическую точность, разграничение знаний и редакционных решений; нет кросс-проектного загрязнения.
3. Несколько последовательных реальных попыток производства; наблюдаемое качество и затраты ручной работы.
4. Нет фиктивной «успешной внешней публикации» и потери принятых референсов/версий.

**Пилотный ориентир для оценки (не требование переписать архитектуру):** 10–20 публикаций/контент-пакетов в реальной эксплуатации по обоим типам, с фактическими решениями и исправлениями. Записать число принятых без правок, повторные генерации, типы ошибок, время подготовки, ошибки внешней доставки и восстановление после рестарта. Порог успеха на коммерческий продукт определить *после* сбора данных.

### Этап II — потенциальный коммерческий продукт (FUTURE / NOT AUTHORIZED FOR BUILD)

Рынок, платёжеспособная аудитория и платная модель — **гипотезы**, пока нет независимого подтверждения пользовательской потребности. После личного пилота: проверить у внешних авторов реальную боль, альтернативы и готовность платить, затем принять отдельное решение о регистрации пользователей, многопроектности SaaS, хранении данных, биллинге, квотах, команде, юридических условиях, API-ограничениях и надёжности.

**Сегодня не реализовывать** логин для разных клиентов, подписки, multi-tenant, тарификацию, организационные роли, массовую генерацию аватаров ради коммерциализации. Границы коммерциализации не служат оправданием новых абстракций.

## 6. Критерии приёмки Content Factory для личного пилота

| ID | Поведение | Доказательство |
| --- | --- | --- |
| CF-01 | Настройки/контекст текущей работы применяются к генерации | Два разных brief без смешения данных |
| CF-02 | Публикация содержит реальный текст и реальное изображение, не stub | Артефакты и их provenance, открываемые файлы |
| CF-03 | QC и человеческое решение относятся к точной ревизии | Проверка UI/API + отрицательный тест |
| CF-04 | EDIT/REGENERATE не перезаписывает принятую историю | Новый revision, старый читается |
| CF-05 | Разрешённый экспорт создаёт полноценный пакет | Изображение + текст, идентификаторы |
| CF-06 | Внешняя публикация отражается как доставленная только при подтверждении провайдера | Fake test + отдельно разрешённый реальный E2E |
| CF-07 | Приложение восстанавливает контент, референсы и решения после перезапуска | Проверка persistent storage |
| CF-08 | Лука и тематическая серия используют общее ядро без взаимного загрязнения | Два независимых E2E/regression |
| CF-09 | Неподтверждённые источники/референсы не становятся фактами/каноном | Негативные тесты |
| CF-10 | Отсутствие платного image provider не блокирует импорт готового визуала | Тест import → QC → approval → export |

**Продуктовая приёмка ≠ текущий заявленный статус v1.0 в README.** Документация и зелёные локальные тесты недостаточны для вывода о пригодности в живом использовании.

## 7. Решение по подходу разработки

Рабочая методология: **пользовательский сценарий → запуск → наблюдаемый факт/ошибка → минимальное исправление → повторный запуск → внешняя проверка**.

- Архитектурный этап ранее завершён; не устраивать новый рефакторинг по гипотетическим рискам.
- Не удалять файлы: только архивирование при необходимости.
- Не терять материал `feature/experience-retrieval-v1` и PR #179.
- Не хранить секреты в репозитории и не выполнять публикацию в реальные аккаунты без разрешения.
- Использовать только доступные бесплатные средства, не предполагать неограниченных API/диска/фоновых задач.
- Ведущая единица результата — **доказанно готовая публикация**, не коммит или схема.
