# 33 — Execution Identity Boundary Decision v0

Status: `CURRENT DECISION — CANDIDATE FOR IMPLEMENTATION`
Date: 2026-09-13

## Decision

For the cross-repository contract, `execution_id` is the identity of a logical execution owned by the Atlas execution boundary. `attempt_id` is the identity of a concrete execution attempt beneath that logical execution.

Therefore:

```text
WorkItem
  → WorkOrder
  → CapabilityRequest
  → execution_id
      → attempt_id (0..n)
          → OutputRevision
```

The existing Atlas `WorkOrder.execution_id` is therefore retained as the execution-level identity. It must not be reinterpreted as an executor-local attempt ID.

## Evidence

Atlas `WorkOrder` is a frozen Core-created contract containing `work_order_id`, `task_id`, `run_id` and `execution_id`. Atlas also has an explicit reconstruction of the WorkOrder → execution → attempt boundary: `WORK_ORDER_ISSUED` precedes `WORKER_STARTED`, which precedes `ATTEMPT_STARTED`; the runtime separately carries `active_execution_id` and `active_attempt_id`. fileciteturn520file0 fileciteturn522file0

Atlas's existing research also confirms that `operation_id` is created at command admission and is upstream of the later runtime chain. The current open question there is the production linkage from admission outcome into durable runtime dispatch, not the existence of `operation_id`. fileciteturn523file0

The Atlas implementation derives `work_order_id` from `execution_id`, further demonstrating that the execution identity already has a Core-owned role in the current model. fileciteturn524file0

External provenance research supports keeping logical activities distinct from concrete generated entities and from responsible agents. W3C PROV explicitly distinguishes Activities, Entities and Agents and supports explicit generation, usage, derivation and responsibility relations. citeturn0search0turn0search3

## Rationale

This preserves four different meanings:

- `operation_id`: command/admission-level identity;
- `run_id`: Atlas run/session-level runtime identity;
- `execution_id`: one logical execution requested by the WorkOrder;
- `attempt_id`: one concrete attempt to perform that execution.

The executor can retry or resume an execution without forcing the cross-repository contract to treat every attempt as a new logical execution.

The output layer can then preserve both:

```text
output_revision_id → execution_id
output_revision_id → attempt_id (when available)
```

This allows exact-output verification without collapsing retries into the same artifact revision.

## Consequences

### I02
Factory → Atlas must provide the canonical WorkItem identity/revision. Atlas creates the WorkOrder and its logical `execution_id` within its existing execution boundary.

### I03
Atlas → Executor CapabilityRequest must carry `execution_id`. The executor may create `attempt_id` values but must preserve the supplied execution identity.

### I04
Capability output must bind to `execution_id`; when the executor exposes an attempt identity, the output record should also carry `attempt_id`.

### Recovery
A retry of the same logical execution may create a new `attempt_id`. A new logical execution must create a new `execution_id`. An external effect with unknown outcome still requires reconciliation before retry, regardless of these identities.

## Non-decisions

This decision does NOT establish:

- a global identity service;
- one database across repositories;
- a global event bus;
- that `execution_id` must be generated by the executor;
- that `attempt_id` must become a globally persistent object;
- that `operation_id`, `run_id` and `execution_id` should be collapsed into one identifier.

## Implementation gate

Before changing runtime code, the following must be proven in the repositories:

1. Factory WorkItem revision can be carried into Atlas without mutation.
2. Atlas can create a WorkOrder bound to that WorkItem revision.
3. Atlas can create and persist `execution_id` before executor dispatch.
4. Executor accepts the supplied execution identity and generates only local/concrete `attempt_id` values where needed.
5. A produced OutputRevision can be traced to both execution and attempt without ambiguity.
6. Existing Factory verification remains exact-output-revision bound.

No runtime code is changed by this decision record.
